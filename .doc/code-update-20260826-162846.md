## 4. New and Optimized Content

### 4.1 首次自动备份立即执行

- 之前：调度器首次读取到有效配置时，只设置“当前时间 + 上传间隔”为下一次上传时间，然后直接跳过本轮。应用重启、重新启用或配置重新识别都会从头等待完整间隔。
- 现在：首次读取到有效配置时立即进入上传流程，并把下一次上传安排在配置间隔之后。
- 原因：避免应用重启或配置变化不断重置倒计时，导致用户长时间看不到任何自动备份。
- 影响范围：客户端后台自动上传；手动上传流程保持不变。

### 4.2 配置变化重新建立自动上传计划

- 调度身份现在包含服务器地址、访问令牌、用户名和上传间隔。
- 上述任一值发生变化后，会立即尝试一次上传，再从新的配置开始计算后续间隔。
- 自动上传失败后的下一次计划仍保持原有间隔，避免短时间高频重试服务器。

### 4.3 调度回归测试

- 新增测试覆盖：首次建立计划立即到期；开始后 1 分钟不会重复上传；到达 30 分钟后再次到期。
- 未新增第三方依赖。

## 5. Fixed Bugs

### 自动备份长时间没有生成云端备份

- 现象：自动备份设置为 30 分钟，但云端没有看到自动上传；手动上传正常。
- 现场信息：本机同步配置有效且自动备份已启用；诊断时云端可读取到手动备份版本，证明服务器地址、令牌和手动上传链路可用。
- 触发条件：启用自动备份后客户端在间隔到达前重启，或后台首次识别配置后尚未完成整段倒计时。
- 根因：原调度初始化分支只登记未来时间并 `continue`，每次应用启动都会重新从完整间隔开始等待，没有首次自动上传。
- 影响范围：后台自动备份首次执行和应用重启后的执行时机；手动备份不受影响。
- 修复方法：抽取可测试的到期判断；首次建立或关键配置变化时返回“立即到期”，之后按设定间隔执行。
- 回归风险：启用了自动备份的客户端在每次应用启动时会多执行一次上传，这是有意的数据保护行为；上传仍使用现有互斥锁，避免与手动上传并发写入。
- 验证证据：新增调度测试通过；完整 Rust 测试 136 项通过；真实同步服务认证读取成功。真实自动 PUT 未执行，见待办项。
