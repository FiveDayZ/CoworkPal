## 4. New and Optimized Content

1. **剥离外部 LibreHardwareMonitor 程序**
   - 之前：CoworkPal 依赖用户另行安装、以管理员身份运行 LibreHardwareMonitor，并开启 REST Web Server；还保留旧 WMI 回退。
   - 现在：外部 REST/WMI 客户端已删除，CoworkPal 直接启动随安装包分发的助手，不要求用户安装或配置第三方监控程序。
   - 原因：降低部署和使用门槛，消除因 REST 版本、端口、服务状态和 WMI 命名空间差异导致的跨设备失败。
   - 影响范围：Windows CPU/GPU 温度来源、设置界面、构建和安装包。

2. **内置类型化硬件传感器读取**
   - 之前：通过外部程序的展示树、文本标签和接口格式间接识别传感器。
   - 现在：助手引用 `LibreHardwareMonitorLib 0.9.6`，按 `HardwareType.Cpu` / `GpuAmd` / `GpuIntel` / `GpuNvidia` 和 `SensorType.Temperature` 读取；CPU 优先 `Core Average`、`Package`、`Tctl/Tdie`，GPU 优先 `GPU Core`，未知但属于正确硬件类型的温度仍可保守使用。
   - 原因：与 TrafficMonitor 采用的硬件类型和温度传感器边界一致，避免依赖设备名称、语言和 REST 展示结构。
   - 影响范围：不同 CPU/GPU 厂商、型号和传感器命名的兼容性。

3. **提权、生命周期和数据边界**
   - 之前：CoworkPal 本体不提权，CPU 底层传感器是否可读取决于外部 LHM 的启动状态。
   - 现在：仅在用户开启设置后通过 `ShellExecuteExW("runas")` 启动助手；助手监视 CoworkPal 父进程并随其退出；关闭开关会终止助手。拒绝 UAC 后不重复打扰，重新关闭/开启才会再请求。
   - 原因：底层 CPU 寄存器和驱动访问通常需要管理员权限，同时保持主应用以普通权限运行。
   - 影响范围：首次启用交互和后台辅助进程。

4. **样本校验和准确性约束**
   - 之前：外部通道可能出现陈旧值，ACPI 平台热区曾被误当作 CPU 温度。
   - 现在：助手原子写入带毫秒时间戳的 JSON；Rust 拒绝超过 10 秒的陈旧样本、异常未来时间、零值、非有限值和大于 `125°C` 的值；ACPI Thermal Zone 回退保持删除。没有可靠 CPU 结果时显示 N/A。
   - 原因：宁可明确缺失，也不展示与 CPU Package/Core 无关的机身热区值。
   - 影响范围：温度展示、告警和依赖温度的宠物状态。

5. **设置迁移和打包**
   - 之前：schema v3 的 `libreHardwareMonitorEnabled` 默认开启，安装包不含传感器 sidecar。
   - 现在：schema v4 使用 `integratedHardwareMonitorEnabled`，默认关闭；旧开关的 true 不迁移为开启。Tauri `externalBin` 包含温度助手，安装包同时包含第三方声明。
   - 原因：升级不应在用户未选择时触发管理员权限请求。
   - 影响范围：旧用户配置升级、CI 和 Windows 安装包。

6. **依赖选择与兼容性**
   - 新增直接依赖：`LibreHardwareMonitorLib 0.9.6`，用途是复用成熟的 Windows 硬件枚举、驱动访问和跨 CPU/GPU 支持。
   - 选择原因：TrafficMonitor 已采用同类方案；自行实现 MSR/PCI/驱动支持风险高，系统 ACPI 热区又不能代表 CPU 核心温度。继续连接外部 LHM 会保留用户安装和配置负担。
   - 许可证：MPL-2.0；包未修改，声明和对应源码地址随应用分发。
   - 主要传递依赖：DiskInfoToolkit 1.1.2、HidSharp 2.6.4、Mono.Posix.NETStandard 1.0.0、RAMSPDToolkit-NDD 1.4.2、System.IO.Ports 10.0.3、System.Management 10.0.2、System.Threading.AccessControl 10.0.3；完整解析结果已锁定在 `packages.lock.json`。
   - 兼容性：目标为 Windows x64、.NET 8 自包含单文件；关闭 trimming，避免反射、硬件枚举和不同设备路径被裁剪。代价是助手约 `35.17 MiB`，最终 NSIS 安装包约 `61.43 MiB`。

## 5. Fixed Bugs

### 5.1 外部 LHM 状态导致 CoworkPal 温度源不可用

- 错误现象：未安装 LHM、LHM 未运行、未提权或 REST 未开启时，高精度温度读取失败。
- 触发条件：用户没有完成外部程序的安装和三步配置，或外部接口状态变化。
- 根因：CoworkPal 运行时依赖另一个应用及其 REST/WMI 接口。
- 影响范围：CPU 温度；通过新助手也补充 AMD/Intel GPU 温度回退。
- 修复方法：删除外部 REST/WMI 客户端，打包并按需启动内置助手。
- 回归风险：新助手需要 UAC；用户拒绝或硬件本身不暴露受支持传感器时仍显示 N/A。
- 验证证据：独立 sidecar 在没有外部 LHM 进程的情况下退出码为 0，并写出 `gpuTemperatureCelsius: 56`；新安装包已生成并包含 sidecar 配置。

### 5.2 ACPI 平台热区被误当作 CPU 温度

- 错误现象：部分设备会显示与 CPU Package/Core 明显不一致的热区温度。
- 触发条件：真实 CPU 传感器不可用，但 Windows Thermal Zone 计数器存在。
- 根因：平台/机身 ACPI 热区被当成 CPU 温度回退。
- 影响范围：CPU 温度显示和高温告警。
- 修复方法：删除 PDH Thermal Zone 通道，并在系统组件选择中拒绝 ACPI/thermal zone 标签。
- 回归风险：传感器不可用的设备改为显示 N/A，不再给出看似有效的估算值。
- 验证证据：当前机器助手非提权样本为 `cpuTemperatureCelsius: null`，未重新出现旧的 ACPI 数值；相关 Rust 筛选测试通过。

### 5.3 陈旧或异常温度样本继续参与展示

- 错误现象：辅助进程退出、文件未更新或传感器返回 0/异常值时，界面可能继续使用无效数据。
- 触发条件：助手停止、写入中断、系统时间偏差或传感器失效。
- 根因：缺少跨进程样本的新鲜度和数值边界校验。
- 影响范围：CPU/GPU 温度显示和温度告警。
- 修复方法：原子替换 JSON，并在 Rust 侧校验时间戳、有限性和 `0 < 温度 <= 125`。
- 回归风险：系统时间发生大幅跳变时会暂时显示 N/A，后续新样本会自动恢复。
- 验证证据：`accepts_fresh_plausible_sample`、`rejects_stale_and_zero_sensor_values` 单元测试通过。

部分设备 CPU 不可读的问题已从“依赖 REST 展示树和设备命名”调整为“使用上游类型化硬件枚举”，但尚未在多种真实 CPU 上执行，因此本记录不将“所有设备 CPU 均可读取”列为已验证修复。

## 8. Supplementary Remarks

- CoworkPal 已不再要求安装、启动或配置 LibreHardwareMonitor 应用，但内部温度助手仍复用开源 `LibreHardwareMonitorLib`。这是“剥离外部程序、内置采集能力”，不是从零重写硬件驱动。
- 未引入新的 Rust crate 或前端 npm 包；`pnpm-lock.yaml` 未变化。NuGet 依赖由独立 `packages.lock.json` 固定。
- `PublishTrimmed=false` 是有意的兼容性选择。硬件库涉及反射、平台 API、原生组件和大量型号分支，裁剪可能只在部分设备上暴露运行失败。
- 助手默认关闭，启用时才触发 UAC；拒绝后不会周期性重复弹窗，关闭再开启可重新尝试。
- 不需要数据库迁移。首次加载旧设置后，`settings.json` 会升级为 schema v4，并以 false 初始化新开关。
- 第三方包选择、许可证、源码位置和传递依赖详见 `hardware-monitor-helper/THIRD_PARTY_NOTICES.md` 与 `hardware-monitor-helper/packages.lock.json`。
